**Q1.** Why is evaluating RAG pipelines important in production environments?

- To prevent negative business impacts that can result from system failures, such as hallucinations or using untrustworthy information.
- To eliminate the need for extensive data collection and storage.
- To ensure the system always produces the same response for the same input.
- To eliminate the need for human review by making the pipeline completely autonomous.

✅ CORRECT ANSWER: 1st - To prevent negative business impacts from system failures such as hallucinations or untrustworthy information.

Evaluation is a safety net: it catches wrong/made-up answers BEFORE they hurt customers or the business. It doesn't remove human review and LLMs are never 100% identical every time.

**Q2. (SELECT ALL)** Which of the following are recommended approaches for monitoring and evaluating the performance of a RAG system?

- ☑ Using code-based evaluations where possible, for example software performance metrics like latency and throughput.
- ☑ Collecting both aggregate system metrics and logging detailed component-level information on each prompt the system receives.
- ☐ Using LLM-as-a-judge techniques to produce continuous numerical scores, for example 1 - 100.
- ☑ Implementing thumbs up/down buttons for users to provide binary feedback on response quality.

✅ CORRECT ANSWERS: 1st, 2nd and 4th.

- Code-based checks (latency, throughput) are cheap and exact - use them first.
- Log BOTH the big picture (averages) and the details of every single prompt.
- Thumbs up/down = simple real-user feedback.
- 3rd is the trap: LLM judges are inconsistent with fine-grained scores like 1-100. Prefer simple labels (yes/no, good/bad, or a small scale).

**Q3.** Which of the following best describes a trade-off of using LLM-as-a-judge evaluations in RAG systems?

- They are fully deterministic and always reproducible across different models.
- They require detailed unit tests and schema validations for every output format.
- They are flexible and scalable, but may introduce bias or inconsistencies without a grounded rubric.
- They are the consensus gold standard because they rely on direct human judgment as captured in their training data.

✅ CORRECT ANSWER: 3rd - flexible and scalable, but may introduce bias or inconsistencies without a grounded rubric.

A judge LLM can grade thousands of answers quickly (scalable), but it can be biased or inconsistent unless you give it clear grading rules (a rubric).

**Q4.** What is the primary reason organizations implement dedicated evaluation platforms for their RAG systems?

- To automate system responses without human oversight or intervention.
- To gain observability across the entire pipeline and trace the origin of individual faulty responses.
- To eliminate the need for component-level evaluations in favor of end-to-end testing.
- To create custom datasets without storing intermediate outputs from each component.

✅ CORRECT ANSWER: 2nd - gain observability across the entire pipeline and trace the origin of individual faulty responses.

Observability = being able to see inside the pipeline (retriever, reranker, prompt, LLM) and find WHERE a bad answer came from.

---

**Q5.** What observability strategy is most effective for diagnosing the root cause of a specific low-quality response generated by a RAG system?

- Regularly calculating aggregate metrics like average response latency and hallucination rate.
- Conducting A/B tests to compare different RAG pipeline configurations.
- Implementing detailed logging and tracing to follow a query's path through each pipeline component.
- Collecting human feedback on a sample of responses.

✅ CORRECT ANSWER: 3rd - detailed logging and tracing to follow a query's path through each component.

For ONE bad answer you need to follow that query step by step: what did the retriever return? what prompt was built? what did the LLM say? Averages, A/B tests and samples tell you THAT something is wrong, not WHY.

**Q6. (SELECT ALL)** Which statements about quantization of large language and embedding models are accurate?

- ☑ Integer quantization reduces the precision of embedding vectors or model parameters, resulting in smaller file sizes and lower memory requirements.
- ☐ Quantized models significantly underperform compared to their full-precision counterparts, making them suitable only for non-critical applications.
- ☑ Quantization enables faster inference and search operations while typically maintaining acceptable quality for most production use cases.
- ☐ Implementing quantization requires specialized hardware accelerators that are rarely available from major cloud providers.

✅ CORRECT ANSWERS: 1st and 3rd.

Quantization = store numbers with less precision (e.g. 32-bit decimals → 8-bit integers): smaller, faster, cheaper, and the quality drop is usually small. It does NOT need rare hardware.

**Q7. (SELECT ALL)** Which approaches could effectively reduce LLM costs in a production RAG system?

- ☐ Increasing the number of documents retrieved to improve accuracy.
- ☐ Using a larger language model, as in one with more parameters, with better comprehension abilities.
- ☑ Implementing a router that only performs retrieval when necessary for complex queries.
- ☑ Using a dedicated endpoint once your system is processing a large enough number of prompts to justify it.

✅ CORRECT ANSWERS: 3rd and 4th.

- More documents = more tokens sent to the LLM = MORE cost.
- A bigger model = MORE cost.
- A router skips retrieval/work when it isn't needed = cheaper.
- At high volume, a dedicated endpoint is cheaper than paying per request.

---

**Q8. (SELECT ALL)** Which approaches could effectively reduce vector database costs in a production RAG system?

- ☑ Only moving vectors or documents into fast memory like RAM when it is necessary for system performance.
- ☐ Using a smaller chunk size when chunking your documents before vectorizing.
- ☑ Using a multi-tenant approach to dynamically move tenants' data into faster, more expensive memory only when needed.
- ☐ Using a smaller top-k when retrieving documents from the knowledge base.

✅ CORRECT ANSWERS: 1st and 3rd.

RAM is the expensive part of a vector DB, so keep only "hot" data in RAM and move the rest to cheaper storage. Smaller chunks = MORE vectors = more cost. A smaller top-k saves LLM tokens, not vector-database storage cost.

**Q9.** You are working to reduce the latency of your RAG system. Which of the following techniques is LEAST likely to help you reduce system latency?

- Replacing your core LLM with smaller or quantized models.
- Using agentic components like a router LLM to sometimes skip unnecessary steps in your overall system.
- Caching prompts and responses to skip time-consuming generation steps for repeatedly submitted prompts.
- Removing rarely accessed documents from your vector database.

✅ CORRECT ANSWER: 4th - Removing rarely accessed documents from your vector database.

Smaller model = faster. Router skipping steps = faster. Caching = instant repeat answers. Removing rarely used documents mostly saves storage COST; it barely changes how fast a search runs (ANN search is already fast).

**Q10.** Your company is considering building a RAG system whose knowledge base will contain highly sensitive documents. Which of the following statements about the security of that information are accurate?

- Encrypting the document text is sufficient to protect your vector database in the case that a hacker gains direct access to it.
- LLMs can be viewed as the "first line of defense" to protect the information in your knowledge base.
- Running an LLM locally yourself ensures the data inside your knowledge base never leaves your own hardware.
- Data from different tenants should be kept in a single index and access privileges managed using metadata filtering.

✅ CORRECT ANSWER: 3rd - Running an LLM locally ensures the data never leaves your own hardware.

- 1st is false: the vectors (embeddings) can leak information too, so encrypting only the text is not enough.
- 2nd is false: an LLM is not a security tool and can be tricked.
- 4th is false: different tenants should be separated (multi-tenancy / separate indexes), not mixed in one index.

## Quick memory cheat-sheet

| Topic | One-line memory |
|---|---|
| Why evaluate | catch hallucinations before they hurt the business |
| Monitoring | code metrics + logs + thumbs up/down; skip 1-100 LLM scores |
| LLM-as-a-judge | scalable but biased without a rubric |
| Observability | trace each query through every component |
| Quantization | smaller + faster, quality mostly kept |
| Cut LLM cost | router, dedicated endpoint (NOT more docs, NOT bigger model) |
| Cut vector DB cost | RAM only when needed, multi-tenant hot/cold |

| Security | local LLM keeps data in-house; separate tenants; encrypt vectors too |
